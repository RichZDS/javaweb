# 接口性能实测

> 前半部分是在开发机上、用 **H2 内存库（MySQL 兼容模式）** 测出来的数字，用来说明业务代码和 SQL 本身的开销。
> 服务器上 MySQL 8 的实测见文末「服务器实测」。

## 结论

8 个常用接口在 1 万道题、200 个学员、10 万条作答记录的数据量下，三次测试里**最差的 95 分位是 69.9 ms**，
中位数都在 35 ms 以内，全部达到“常用接口 0.5 秒内返回”的目标（`docs/spec.md` 非功能要求）。
没有接口超标，所以这次**没有改索引、没有新增迁移脚本**。

## 测法

- 每个接口先预热 10 次（让 JIT 编译和各种缓存就位），再连续测 50 次，记录每次从发出请求到收完响应的时间。
- 中位数 = 50 个值排序后第 25、26 个的平均；95 分位用最近秩法，取第 ⌈0.95 × 50⌉ = 48 个值。
- 所有请求都必须成功（2xx），否则测试直接失败，所以表里没有失败请求。
- 各接口的场景：
  - 分类树：一个有 500 条作答的学员取自己目标考试的整棵树（含每个节点的题量、已做数、正确率）。
  - 开随机练习：每次换一个学员，在一个科目（约 833 道题）里随机抽 20 题，返回带渲染好 HTML 的整套题。
  - 提交答案：在 50 题的练习里逐题提交，包括判分、写作答记录、更新错题本、检查是否做完。
  - 统计总览 / 按日 / 薄弱点：同一个学员，范围是目标考试（约 3 333 道题、该学员 500 条作答）。
  - 开考：每次换一个学员开规则卷，含按规则从约 3 333 道题里不重复抽 50 道、写快照。
  - 交卷结算：每场 50 题都已有答案，结算含判分、写 50 条作答记录、答错的进错题本、写总分。

## 分析

- 最慢的是“交卷结算”和“开考”，中位数 22–34 ms：结算要逐题写作答记录和更新错题本（约 100 条 SQL），开考要按规则从三千多道题里抽题再序列化快照。
- 95 分位明显高于中位数（约 2–7 倍），三次运行里单次最慢的请求是 118.3 ms（第 1 次的分类树）。主要是共享机器上的调度抖动和 GC：测试进程是低优先级（nice 15），同时还有别的构建在跑。
- 统计类接口都按 `(user_id, root_category_id, graded_at)` 和 `(user_id, question_id, graded_at)` 两个已有索引过滤，每次只扫描本人的几百条记录，所以和全表 10 万条的规模关系不大。

## 可能的改进（目前不需要）

如果到了服务器上某个接口接近 0.5 秒，先看这几处：

1. 交卷结算的作答记录可以改成批量插入，错题本的更新也可以合并，能把一次结算的 SQL 从约 100 条降到个位数。
2. 分类树每次都现查全部分类和题量；分类很少变，可以加一个带失效的内存缓存。
3. `studyDays` 和按日统计对 `graded_at` 做了 `+8 小时` 再取日期，用不上索引的排序，但已经按用户过滤；
   单个用户的作答达到几万条时，可以加一张按天汇总的表。

## 服务器实测（MySQL 8，2026-11-02，main 82e795f）

结论：同样 8 个接口在服务器上三次测试**最差的 95 分位是 81.5 ms（交卷结算）**，其余都在 32 ms 以内；
20 个学员同时刷题，400 次提交全部成功，95 分位 82.7 ms，后端日志没有报错和死锁。都达到 0.5 秒的目标。

### 环境

| 项 | 值 |
| --- | --- |
| 服务器 | 腾讯云上海，4 核 AMD EPYC 7K62，3.7 GB 内存，测试时负载 0.1–0.7 |
| 容器 | 后端 Temurin 17 JRE，内存上限 640 MB、`-Xmx384m`；MySQL 8.0.46，内存上限 512 MB，`innodb_buffer_pool_size` 128 MB，可重复读；nginx 64 MB |
| 数据 | 正式题库（共 478 道题，含测试同事留下的题），408 规则卷每场 20 题 |
| 测法 | 在服务器本机用 Python 经 nginx（`127.0.0.1:18090`）请求，不经过公网和 HTTPS；新建一个 `perf_` 账号，预热 10 次、计时 50 次，中位数和 95 分位的算法同上 |
| 顺序 | 分类树 → 开练习 → 提交答案 → 开考 + 交卷（每场先把题答完再交）→ 统计。统计时这个账号已有约 1 260 条作答 |

### 和 H2 的差别

- 交卷结算最慢：20 题的结算中位数 42–60 ms，比 H2 上 50 题的 31–34 ms 还慢。
  原因是 MySQL 每次提交要真正落盘，而结算按题逐条写作答记录和错题本（先插入再按条件更新，避免间隙锁死锁）。
  离 0.5 秒还很远，暂不改；以后要提速，就做上面“可能的改进”第 1 条的批量写入。
- 其余接口和 H2 在同一个量级。服务器题量比 H2 测试少（478 道对 1 万道），但统计类接口只扫本人的作答，和总题量关系不大。

### 怎么复现

脚本在 `deploy/perf/`，要在服务器本机跑（经公网跑会把跨境网络的耗时算进去）：

```bash
# 参数：一级分类 id、规则卷 id
ssh <服务器> 'python3 - 1 2' < deploy/perf/bench.py
# 参数：一级分类 id、并发人数
ssh <服务器> 'python3 - 1 20' < deploy/perf/concurrent.py
```

脚本会新建 `perf_` 开头的账号和它们的练习、考试记录。正式数据库上跑完要删掉这些账号，或者像这次一样在正式发布前清库重建时一并清掉。
